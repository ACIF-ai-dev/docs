## Connect

Upgrade `GET /v1/stream` to WebSocket and send your builder API key as a Bearer credential:

```http
Authorization: Bearer <your API key>
```

The stream requires a `trade`-scope key. Keep that key on your server: it is a credential that can reach trading and funding surfaces, not a browser or mobile-app credential.

## Connecting from a browser

Your builder backend, not the browser, sends its trade key to `POST /v1/stream/tickets`, optionally with `userId`. Pass the returned `ticket` to the browser, then connect it without an Authorization header:

```js
new WebSocket("wss://…/v1/stream?ticket=" + encodeURIComponent(ticket));
```

Tickets expire after **60 seconds** and are **one-time use**. Obtain a new ticket for every reconnect. Do not send an API-key header with a ticket. Invalid ticket upgrades return HTTP 401 before upgrade (browsers show this as close **1006**); request a fresh ticket and retry. A ticket `userId` has at most **3** simultaneous connections. A ticket issued without `userId` does not use that per-user limit and only receives the ticket per-subbuilder limit; provide `userId` when you need a per-user limit. Ticket connections have a separate per-subbuilder limit of **500** by default (key connections remain limited to **10**); either ticket limit closes with **4029**. More than **60** ticket attempts from the same IP in a minute return HTTP 429 before upgrade, and a busy ticket verifier returns HTTP 503 before upgrade; browsers show either as close **1006**. Because tickets are URL query parameters, proxy and CDN access logs can contain them; they are one-time and expire in 60 seconds, so a logged value was already used or will soon expire. Tickets are the browser-safe alternative: keep the trade key on your server.

Issuing tickets has its own rate budget: by default 600 `POST /v1/stream/tickets` requests per minute per builder account, separate from the per-key and hourly budgets your other requests use (see **Rate limits** on the API reference home page). Exceeding it returns HTTP 429 with `error.details.reason` set to `stream_ticket_limit_exceeded` and a `Retry-After` header. It is a different limit from the 60 ticket attempts per IP per minute on the upgrade above.

After the upgrade succeeds, the stream sends a `welcome` frame with a `connectionId` and `heartbeatIntervalMs`.

## Send frames

Client frames use `op` as their discriminator, not `type`:

```json
{"op":"subscribe","tokenIds":["token-id"]}
```

```json
{"op":"subscribe","tokenIds":["token-id"],"trades":true}
```

```json
{"op":"unsubscribe","tokenIds":["token-id"]}
```

```json
{"op":"ping"}
```

`trades` is optional and opts those tokens into `trade` frames (see **Trade frames** below); the only accepted value is `true`. A `subscribe` without it behaves exactly as it did before the flag existed.

`subscribe` and `unsubscribe` each require from **1** through **200** token IDs. Each token ID is a string from **1** through **128** characters. A WebSocket frame can be at most **65536** bytes (**64 KiB**).

A token's order book is held with operations of its own (see **Order book frames**):

```json
{"op":"subscribeBook","tokenIds":["token-id"]}
```

```json
{"op":"unsubscribeBook","tokenIds":["token-id"]}
```

`subscribeBook` and `unsubscribeBook` each require from **1** through **4** `tokenIds`, each a token ID string of the length above. A frame with more, with none, or with a value that is not such a string is refused with `VALIDATION_FAILED`. The two operations have no other key: one sent with them, such as `depth` or `trades`, is ignored, and a `book` key on `subscribe` opens no order book.

The service accepts at most **120** client frames in each **1000 ms** window. It sends a WebSocket heartbeat every **30000 ms** and closes a connection that has not answered within **90000 ms**.

## Receive frames

Server frames use `type` as their discriminator:

```json
{"type":"welcome","connectionId":"connection-id","heartbeatIntervalMs":30000}
```

```json
{"type":"subscribed","tokenIds":["token-id"],"snapshot":[{"tokenId":"token-id","bestBid":"0.105","bestAsk":null,"ts":1727430000123}]}
```

```json
{"type":"unsubscribed","tokenIds":["token-id"]}
```

```json
{"type":"pong"}
```

```json
{"type":"price","tokenId":"token-id","bestBid":"0.105","bestAsk":null,"ts":1727430000123}
```

```json
{"type":"resolved","tokenId":"token-id","market":"market-id","winningTokenId":"token-id","winningOutcome":"Yes","ts":1727430000123}
```

```json
{"type":"trade","tokenId":"token-id","side":"BUY","price":"0.07","size":"1234.56","amountUsd":"86.4192","ts":1727430000123}
```

```json
{"type":"error","code":"VALIDATION_FAILED","message":"Invalid stream frame.","details":{}}
```

`details` on an `error` frame is optional. Ignore server frames with an unknown `type` to parse defensively.

## Market frames

A `price` frame is paired with the subscribed `tokenId`. A `best_bid_ask` event with a single `tokenId` is routed through that token. The service sends at most one `price` frame per token every **250 ms**; it keeps the newest price in that window. `resolved` frames are immediate and are not coalesced.

`bestBid` and `bestAsk` are decimal **strings**, or `null` when unavailable. Do not parse them as numbers for calculation. One exception is display only: to continue a price history chart (see **Read price history** on the API reference home page), you can convert both to numbers to place their midpoint on the chart, and a frame where either is `null` adds no point. `ts` is epoch milliseconds: the upstream timestamp when present, otherwise the service receive time. After a snapshot, the service does not send a price with an older timestamp when both the snapshot and new price carry upstream timestamps. A price with the same value as a snapshot can follow it when that price was waiting in a coalescing window.

The `subscribed` frame includes a snapshot for each newly subscribed token with a cached price. A token without a cache entry is omitted. If the upstream sends an order book for a token that has no cached price, the service uses that book's highest bid and lowest ask as the token's first `price` frame. A token that already has a cached price ignores order books; its later prices come from best bid and ask updates. The upstream is not guaranteed to send an order book, and without one the token's first `price` frame follows the next quote change. Read an initial value from REST when a snapshot is empty.

`market_resolved` is forwarded as a `resolved` frame once for each of its subscribed token IDs. If you subscribe to both YES and NO tokens for one market, its resolution arrives in two `resolved` frames, one for each token. Process frames idempotently.

Resolved tokens are omitted from snapshots; obtain their resolution status and final price from REST.

`new_market` does not produce a frame. This is a token-level subscription service: tokens belonging to a newly created market have, by definition, not been subscribed by any client, so there is no token-level recipient to route the event to. The service does not forward upstream `book`, `price_change`, or `tick_size_change` events as they are; for a `subscribe` holding, an upstream `book` only supplies a missing first price, as described above. The order book itself is sent in a shape of its own to connections that ask for it with `subscribeBook` (see **Order book frames**). An upstream `last_trade_price` becomes a `trade` frame only for connections that opted in, as described below.

## Trade frames

A `trade` frame reports one public trade on a token. It is sent only to a connection that subscribed that token with `"trades":true`; a connection that did not opt in receives no `trade` frames, and the frames it does receive are unchanged. The opt-in is per token:

| You send | Effect on `trade` frames for those tokens |
|---|---|
| `subscribe` with `"trades":true` | On, whether or not the token was already subscribed. The reply is the usual `subscribed` frame; a token that was already subscribed is not listed in it again. |
| `subscribe` without `trades` | No change. A token already opted in stays opted in. |
| `unsubscribe` | Off, together with the token's `price` and `resolved` frames. |
| `"trades"` with any value other than `true` | The whole frame is refused with `VALIDATION_FAILED`, as any invalid frame is. |

The opt-in does not count against the 200-token subscription limit separately; only the tokens do.

The frame has these keys and no others. They are the same keys, with the same meaning, as each element of `GET /v1/markets/{marketId}/trades`:

- `tokenId`: the outcome token the trade was on.
- `side`: `"BUY"` or `"SELL"`, as the source reports it.
- `price`, `size`: decimal **strings** (shares for `size`), with no exponent and no trailing zeros.
- `amountUsd`: `price` × `size` in decimal, not rounded, as a decimal string.
- `ts`: the trade time in epoch milliseconds, from the source.

`trade` frames carry no trader identity, transaction hash, or fee rate. An upstream event without a size or a trade time, or with a price or size that is not a plain decimal, is dropped rather than completed with a guessed value. Trade frames are sent as they arrive, without coalescing, and are not part of the `subscribed` snapshot. Their order relative to `price` frames is not guaranteed.

A connection receives at most **50** `trade` frames in each **1000 ms** window; trades beyond that are dropped, not queued. Trade frames are also skipped while the connection's `bufferedAmount` is over half of the **4008** close threshold below. Skipped trades never count toward that close, and they never hold back a `price` frame. A busy market can therefore show gaps in the trade feed: treat it as a live tape, not a complete record.

To show recent trades, read `GET /v1/markets/{marketId}/trades` when the view opens and subscribe with `"trades":true` before or right after that read, then add each `trade` frame to the top. The REST read and the stream can contain the same trade. With no trade ID or transaction hash in either, complete de-duplication is not guaranteed; dropping a frame whose `tokenId`, `side`, `price`, `size`, and `ts` all match an element already shown removes most repeats but can also drop a distinct trade with identical values.

While a new version of the service is being rolled out, an instance that predates the flag ignores `"trades":true` without an error: a connection that lands on it gets the usual `subscribed` frame and no `trade` frame. Keep the REST read as the source of recent trades, and send `subscribe` with `"trades":true` again after every reconnect.

## Order book frames

The order book of an outcome token can be held on the same connection with `subscribeBook` and let go of with `unsubscribeBook` (see **Send frames**). The token ID is the `tokenId` of a market outcome, as for `subscribe`; a Perps instrument's order book is read from `GET /v1/perps/instruments/{instrumentId}/book`. Holding a token's order book and holding its prices are two separate holdings: a `subscribeBook` holding receives the frames of this section and no `price`, `trade`, or `resolved` frame, and a `subscribe` holding receives no `book` frame. Send both operations for a token to receive both.

A connection holds at most **4** order books at a time. They are counted apart from the tokens of `subscribe`: neither counts against the other's limit. A token listed twice, or one whose book the connection already holds, counts once. A token ID is not checked against any market when the frame arrives: any string of the accepted length is held and counted. A `subscribeBook` that would hold more books than the limit is refused with this `error` frame, and nothing in that frame is held:

```json
{"type":"error","code":"RATE_LIMITED","message":"Book subscription limit exceeded.","details":{"reason":"book_subscription_limit","currentSubscriptions":4,"requestedSubscriptions":1}}
```

`currentSubscriptions` is the number of books the connection holds, and `requestedSubscriptions` is the number of IDs in the refused frame.

The reply to `subscribeBook` is a `bookSubscribed` frame:

```json
{"type":"bookSubscribed","tokenIds":["token-id"],"snapshot":[{"tokenId":"token-id","bids":[{"price":"0.10","size":"250","cumulative":"250"}],"asks":[{"price":"0.12","size":"75.5","cumulative":"75.5"}],"ts":1790000000400}],"feed":"live"}
```

- `tokenIds`: the tokens whose book this frame newly holds. A token the connection already held is not listed again and gets no `snapshot` element again; when every listed token was already held, `tokenIds` and `snapshot` are both empty.
- `snapshot`: for each token in `tokenIds` whose book the service has at that moment, that book in the shape of a `book` frame without `type`. A token without one is left out, and its book arrives as its first `book` frame.
- `feed`: `"live"` or `"interrupted"`, the connection's order book word described below. It covers every book the connection holds, not only the newly held ones.

Later frames:

```json
{"type":"book","tokenId":"token-id","bids":[{"price":"0.10","size":"250","cumulative":"250"},{"price":"0.09","size":"1000","cumulative":"1250"}],"asks":[{"price":"0.12","size":"75.5","cumulative":"75.5"}],"ts":1790000000650}
```

```json
{"type":"bookFeed","state":"interrupted","ts":1790000001000}
```

```json
{"type":"bookUnsubscribed","tokenIds":["token-id"]}
```

A `book` frame is the whole top of one token's order book, never a change to apply: replace what you show for that `tokenId` with it, and do not append. Besides `type`, it has these keys and no others:

- `tokenId`: the outcome token the book belongs to.
- `bids`, `asks`: at most **10** levels per side, best first: bids descending by price, asks ascending. Levels beyond that are not sent. A side can be empty, and a book with both sides empty is sent as it is (`"bids":[],"asks":[]`), in a `snapshot` and as a `book` frame.
- Each level has `price`, `size` (shares), and `cumulative`, all decimal **strings**. `price` and `size` are kept as the source sends them, so trailing zeros (`"0.50"`, `"250.0"`) or a missing leading zero (`".4"`) can appear: parse them as decimals, and do not compare them as text. `cumulative` is the sum of `size` from the best level of that side through this one, as a plain decimal with no exponent and no trailing zeros.
- `ts`: epoch milliseconds, the time of the latest event the service applied to that book: the source's timestamp when it carries one, otherwise the service receive time. It is not guaranteed to increase from one frame to the next.

The service sends at most one `book` frame per token every **250 ms**, the coalescing window of `price` frames. The frame carries the top as it stands at the end of that window, and it is sent only when that top changed, in the `price` or `size` text of a level: a change below the levels a frame carries, or one undone within the window, sends nothing. A `book` frame can still equal the book you already have, right after `bookSubscribed` when a change was waiting in its window, or after an interruption (see below). Replacing makes that harmless.

`book` frames follow the buffer rule of `price` frames and count toward the same **4008** close (see **Disconnections**). A frame skipped that way is not sent again; the token's next `book` frame arrives when its top changes again. A `subscribeBook` that arrives while the connection is over that buffer threshold is answered with its true `tokenIds` and `feed` and an empty `snapshot`, and that snapshot is not sent later either. After you have caught up on reads, send `unsubscribeBook` and then `subscribeBook` for the tokens to receive a fresh `snapshot`.

A `bookUnsubscribed` frame lists the tokens whose book `unsubscribeBook` let go of; a token whose book the connection did not hold is left out, so the list can be empty.

`bookSubscribed.feed` and `bookFeed.state` are one word for the connection, about the order books it holds:

| Word | Meaning | What to do |
|---|---|---|
| `"interrupted"` | The service cannot vouch for at least one book the connection holds: that book became unknown to the service, and no fresh `book` frame for it has gone out since. | A book you show can be stale. The frame does not name the token, so the safe reading is every book you hold. A `book` frame that arrives after it is current for its token. |
| `"live"` | For every book the connection holds, the service has a book and has sent it out since that book last became unknown. | What you show is current, within the two limits described below: a `book` frame skipped for a connection over the buffer threshold, and a gap the word does not report. |

`bookFeed` is sent only when the connection's word changes, and only to a connection that holds at least one order book. `bookSubscribed.feed` is the word right after the subscribe, and no `bookFeed` frame repeats it. `"live"` is sent after the fresh `book` frame has gone out, never before it; a connection over the buffer threshold is the one case in which the word arrives without that frame (see below). `ts` is the service time of the change in epoch milliseconds. Show a live indicator from `feed` and `bookFeed`, not from the arrival of `book` frames: a quiet book sends none.

A book becomes unknown to the service in three cases:

- **It is first held.** The service keeps a token's order book only while some connection holds it with `subscribeBook`; holding the token's prices with `subscribe` does not keep it. The first connection to hold a token's book is therefore always answered with no `snapshot` element for that token and `feed` `"interrupted"`, then receives the token's `book` frame, then `bookFeed` `"live"` once every book it holds has been sent. A connection that subscribes while the book is kept receives it in `snapshot`.
- **The service's own reading of that token's book ended or had to be started again.** This is a failure, not a routine event. Each connection holding that token's book whose word was `"live"` receives `bookFeed` `"interrupted"`; the fresh `book` frame follows, then `bookFeed` `"live"` once every book the connection holds has been sent again.
- **The service can no longer vouch for the levels it keeps.** It cannot tell that they are the token's true top levels, or an update of that book reached it in a form it could not read. This is rare, and the frames are the same as in the previous case.

Nothing another connection does makes a book unknown. No `subscribe` or `unsubscribe`, and no `subscribeBook` or `unsubscribeBook`, by any connection and for any token, interrupts a book you hold. Holding one more book on your own connection does not interrupt the ones it already holds either: a `bookSubscribed` with `feed` `"interrupted"` on a connection that was `"live"` is about the newly held books, and the `book` frames of the others keep arriving meanwhile.

The first `book` frame of a newly kept book arrives when the source next sends that token's book. No time bound is promised for it, and on a quiet market it can take long. Until then, and for as long as a held token ID names no order book at all, the word stays `"interrupted"` for the whole connection while the other books it holds keep being sent: show each token for which you have a `snapshot` element or a `book` frame, and treat a token with neither as not loaded yet. The word reports the three cases above. It is not a promise that every delay or gap between the source and the service is reported, so do not read `"live"` as proof that a book that has stopped changing is unchanged at the source.

When `unsubscribeBook` lets go of the only book that kept the word at `"interrupted"` and the connection still holds others, `bookFeed` `"live"` is sent before `bookUnsubscribed`. Letting go of the last book sends no `bookFeed`. `bookFeed` is sent whatever the connection's buffer holds, while a `book` frame is skipped over the buffer threshold: a connection that is not reading fast enough can receive `"live"` without the fresh `book` frame, and the catch-up step above applies.

A token's `price` frames and its `book` frames are produced separately. No order between them is promised, and neither is agreement at an instant between `bestBid` and `bestAsk` of a `price` frame and the best levels of a `book` frame.

`GET /v1/markets/{marketId}/book` (see **Read the order book** on the API reference home page) did not change and remains the way to read an order book once; its levels carry `price` and `size` without `cumulative`. Read it for an initial value when a `snapshot` is empty.

Order book holdings belong to one connection. After every reconnect send `subscribeBook` again and replace your books with the new `snapshot`. While a new version of the service is being rolled out, an instance that predates these operations answers both with `VALIDATION_FAILED`.

## Perps frames

Perps instruments use their own operations on the same connection:

```json
{"op":"subscribePerps","instrumentIds":["12","7"]}
```

```json
{"op":"subscribePerps","instrumentIds":["12"],"trades":true}
```

```json
{"op":"unsubscribePerps","instrumentIds":["7"]}
```

`subscribePerps` and `unsubscribePerps` each require from **1** through **10** `instrumentIds`, each an `instrumentId` string as listed by `GET /v1/perps/instruments`. An identifier that is not a decimal string of that form (no sign, no leading zero) refuses the whole frame with `VALIDATION_FAILED`; a well-formed identifier is not checked against the list, and one that names no instrument is held and counted like any other but receives no `perpsPrice` or `perpsTrade` frames. An identifier listed twice counts once. A connection holds at most **10** instruments at a time: a `subscribePerps` that would hold more is refused with an `error` frame whose `code` is `RATE_LIMITED` and whose `details` carry `reason` `perps_subscription_limit`, `currentSubscriptions`, and `requestedSubscriptions`. The token operations above are unchanged. Tokens and Perps instruments are counted separately: neither counts against the other's limit.

`trades` is optional and opts the listed instruments into `perpsTrade` frames; the only accepted value is `true`, and any other value refuses the whole frame with `VALIDATION_FAILED`. It turns trades on for every listed instrument, including one the connection already holds. A `subscribePerps` without it leaves trades as they were. `unsubscribePerps` turns off an instrument's prices and trades together.

The reply to `subscribePerps` is a `perpsSubscribed` frame:

```json
{"type":"perpsSubscribed","instrumentIds":["12"],"snapshot":[{"instrumentId":"12","lastPrice":"118630.5","markPrice":"118633.00","indexPrice":"118631.10","fundingRate":"-0.0000125","nextFundingTs":1790003600000,"ts":1790000000400}],"trades":[{"instrumentId":"12","side":"long","price":"118630.5","quantity":"0.015","amountUsd":"1779.4575","ts":1790000000500},{"instrumentId":"12","side":"short","price":"118629","quantity":"0.2","amountUsd":"23725.8","ts":1790000000450}],"feed":"live"}
```

- `instrumentIds`: the instruments this frame added. An instrument the connection already holds is not listed again.
- `snapshot`: for each instrument in `instrumentIds` that the service has a price for, that price in the shape of a `perpsPrice` frame without `type`. An instrument without one is omitted; read its `ticker` from `GET /v1/perps/instruments` for an initial value.
- `trades`: only when the frame carried `"trades":true`. For each instrument whose trades this frame turned on, up to **5** of its most recent public trades, newest first, each in the shape of a `perpsTrade` frame without `type`. An instrument whose trades were already on is not listed again.
- `feed`: `"live"` or `"interrupted"`, the state of the service's Perps upstream when the frame was sent.

Later frames:

```json
{"type":"perpsPrice","instrumentId":"12","lastPrice":"118630.5","markPrice":"118633.00","indexPrice":"118631.10","fundingRate":"-0.0000125","nextFundingTs":1790003600000,"ts":1790000000400}
```

```json
{"type":"perpsTrade","instrumentId":"12","side":"short","price":"118640","quantity":"1","amountUsd":"118640","ts":1790000000900}
```

```json
{"type":"perpsUnsubscribed","instrumentIds":["12"]}
```

```json
{"type":"perpsFeed","state":"interrupted","ts":1790000001000}
```

A `perpsPrice` frame carries the values of an instrument's `ticker` in `GET /v1/perps/instruments`, with the same key names and notation: `lastPrice`, `markPrice`, `indexPrice`, and `fundingRate` are decimal **strings** exactly as the source reports them, trailing zeros included, and `fundingRate` can be negative. `nextFundingTs` is epoch milliseconds, and `ts` is the time of the source frame in epoch milliseconds. The service sends at most one `perpsPrice` frame per instrument every **250 ms**, with the newest values in that window, and only when at least one of `lastPrice`, `markPrice`, `indexPrice`, `fundingRate`, and `nextFundingTs` changed. A price the service cannot read in full is not sent rather than completed with a guessed value.

A `perpsTrade` frame reports one public trade on an instrument the connection holds with `"trades":true`. If the service carries no trades for an instrument, `"trades":true` is accepted for it, but its `trades` list stays empty and no `perpsTrade` frame arrives. Besides `type`, the frame has these keys and no others:

- `instrumentId`: the instrument the trade was on.
- `side`: `"long"` or `"short"`, as the source reports it.
- `price`, `quantity`: decimal **strings** (base-asset units for `quantity`), with no exponent and no trailing zeros. This notation differs from `perpsPrice`, which keeps the source's text.
- `amountUsd`: `price` × `quantity` in decimal, not rounded, as a decimal string.
- `ts`: the trade time in epoch milliseconds, from the source.

`perpsTrade` frames carry no trade identifier, trader identity, or transaction hash. A trade the service cannot read in full is dropped rather than completed with a guessed value. At most **50** `perpsTrade` frames are sent per connection in each **1000 ms** window, counted apart from `trade` frames; trades beyond that are dropped, not queued. Like `trade` frames, they are skipped while the connection's `bufferedAmount` is over half of the slow-consumer threshold in **Disconnections**, and skipped trades never count toward that close. `perpsPrice` frames follow the buffer rule of `price` frames and count toward the same close. Treat the trades as a live tape, not a complete record.

A trade listed in `perpsSubscribed.trades` is not sent again as a `perpsTrade` frame, and a trade the source repeats after the service reconnects to it is dropped. The list in `perpsSubscribed.trades` is the instrument's recent trades, not only the ones this connection has not seen: after your own reconnect, or after `unsubscribePerps` followed by a new `subscribePerps` with `"trades":true`, replace your trade list with the new `trades` rather than adding to it. Recent trades are kept in memory only: after the service restarts, the list holds only the trades it has read since.

A `perpsUnsubscribed` frame lists the instruments that `unsubscribePerps` let go of; an instrument the connection did not hold is left out.

`perpsFeed` reports the service's own Perps upstream: `"interrupted"` whenever the upstream is not delivering, including while the service is starting, and `"live"` when it delivers. A connection that subscribes during start-up can therefore see `"interrupted"` followed by a first `"live"`. It is sent only when that state changes, and only to connections that hold at least one Perps instrument. After `"live"`, the next price of each held instrument is sent even when it did not change. Trades during an interruption are not sent later. Show a live indicator from `perpsSubscribed.feed` and `perpsFeed`, not from the arrival of frames.

When Perps market data is not open on this deployment, `subscribePerps` is answered with an `error` frame whose `code` is `NOT_FOUND` and whose `details.reason` is `perps_not_open`, and `unsubscribePerps` is answered with a `perpsUnsubscribed` frame with an empty `instrumentIds`. While a new version of the service is being rolled out, an instance that predates these operations answers both with `VALIDATION_FAILED`; send `subscribePerps` again after every reconnect.

## Crypto round frames

The recurring crypto Up or Down rounds of `GET /v1/markets/rounds` (see **Crypto rounds** on the API reference home page) can be followed on the same connection:

```json
{"op":"subscribeRounds","pairs":[{"asset":"BTC","interval":"5m"},{"asset":"SOL","interval":"5m"}]}
```

```json
{"op":"unsubscribeRounds","pairs":[{"asset":"SOL","interval":"5m"}]}
```

`subscribeRounds` and `unsubscribeRounds` each require from **1** through **8** `pairs`. Each pair has exactly the keys `asset` (1 to 10 upper-case letters or digits, such as `BTC`) and `interval` (`5m` is the only value); a pair of another form refuses the whole frame with `VALIDATION_FAILED`. A pair this deployment does not carry also refuses the whole frame with `VALIDATION_FAILED`, for `unsubscribeRounds` as well as `subscribeRounds`, and nothing in that frame is subscribed or unsubscribed. A pair listed twice counts once. A connection holds at most **8** pairs at a time: a `subscribeRounds` that would hold more is refused with an `error` frame whose `code` is `RATE_LIMITED` and whose `details` carry `reason` `rounds_subscription_limit`, `currentSubscriptions`, and `requestedSubscriptions`. Tokens, Perps instruments, and round pairs are counted separately: none counts against another's limit.

The reply to `subscribeRounds` is a `roundsSubscribed` frame:

```json
{"type":"roundsSubscribed","pairs":[{"asset":"BTC","interval":"5m"}],"snapshot":[{"asset":"BTC","interval":"5m","state":"ok","fetchedAt":"2026-10-02T10:12:03.000Z","current":{"marketId":"516710","eventId":"903193","slug":"btc-updown-5m-1790935800","eventStartTime":"2026-10-02T10:10:00.000Z","endDate":"2026-10-02T10:15:00.000Z","status":"live","targetPrice":null,"targetPriceSource":null,"outcomes":[{"outcome":"Up","tokenId":"71453-example"},{"outcome":"Down","tokenId":"71454-example"}],"winningOutcome":null},"next":[],"past":[]}]}
```

- `pairs`: the pairs this frame added. A pair the connection already holds is not listed again.
- `snapshot`: for each pair in `pairs`, the element `GET /v1/markets/rounds` returns for it, with the same keys; `targetPrice` can differ from the REST list from a round's start until Polymarket publishes its value (see below). If the service could not yet evaluate a pair, the pair is listed in `pairs` without an element in `snapshot`; every round of that pair then arrives as a `roundUpdate` frame once an evaluation succeeds.

Later frames:

```json
{"type":"roundUpdate","asset":"BTC","interval":"5m","round":{"marketId":"516710","eventId":"903193","slug":"btc-updown-5m-1790935800","eventStartTime":"2026-10-02T10:10:00.000Z","endDate":"2026-10-02T10:15:00.000Z","status":"ended","targetPrice":"118420.15","targetPriceSource":"polymarket","outcomes":[{"outcome":"Up","tokenId":"71453-example"},{"outcome":"Down","tokenId":"71454-example"}],"winningOutcome":null},"ts":1790936103000}
```

```json
{"type":"roundsUnsubscribed","pairs":[{"asset":"SOL","interval":"5m"}]}
```

A `roundUpdate` frame carries one round of a held pair, with the same keys as a round of the REST list, whenever any of its keys changed: a new round appears, its `status` moves (`upcoming`, `live`, and `ended` change at the window's boundaries without any read from Polymarket), it gets its `targetPrice`, its `targetPrice` is replaced, or it gets its `winningOutcome`. Replace the round with the same `marketId`. The service evaluates the held pairs every **1000 ms**, so a change reaches you within about a second of the service knowing it; a `polymarket` target price or result is known only after Polymarket publishes it and the service reads it, which can be minutes after the round ends. When several rounds change at once, they arrive oldest first. `ts` is the time of that evaluation in epoch milliseconds. No frame announces a round leaving the list, and the pair's `state` and `fetchedAt` are not sent again: keep the newest **5** ended rounds yourself, and read the REST list when you need the pair's own keys. From a round's start this stream can carry `targetPriceSource` `polybolt_twap` when the deployment enables it: the first `chainlink_twap_60s` reference price (see **Reference price frames**) this instance received that was stamped at or after the round's start and less than **2000 ms** after it, excluding a value the source marks as carried forward. A later-arriving point with an earlier stamp does not replace it. It is an estimate that Polymarket's own value (`polymarket`) replaces when published (one more `roundUpdate`). If no such point reached this instance (it was not connected, or it restarted during the round), the target stays `null` until Polymarket publishes. `GET /v1/markets/rounds` never returns `polybolt_twap`. Keep values by this precedence across reconnects to instances that may be behind or ahead: `polymarket` is final and never replaced; `polybolt_twap` replaces `null` and is replaced by `polymarket` or by a `polybolt_twap` in a later frame (only another instance can send a different value); `null` never replaces a value you have seen. A non-null `winningOutcome` is also final.

`roundUpdate` frames follow the buffer rule of `price` frames and count toward the same close, and a skipped frame is not sent again. After a reconnect, or if you suspect you missed one, send `unsubscribeRounds` and then `subscribeRounds` for the pair to receive a fresh `snapshot`.

A `roundsUnsubscribed` frame lists the pairs that `unsubscribeRounds` let go of; a carried pair the connection did not hold is left out.

These frames carry no prices, trades, or settlement. For the underlying price see **Reference price frames**; for token prices and trades, send `subscribe` with a round's `outcomes[].tokenId`, adding `"trades":true` for `trade` frames, and subscribe to the tokens of a `next` round before it starts so there is no gap when it becomes `current`.

When crypto rounds are not open on this deployment, a well-formed `subscribeRounds` is answered with an `error` frame whose `code` is `NOT_FOUND` and whose `details.reason` is `rounds_not_open`, whichever pairs it names, and `unsubscribeRounds` is answered with a `roundsUnsubscribed` frame with an empty `pairs`. While a new version of the service is being rolled out, an instance that predates these operations answers both with `VALIDATION_FAILED`; send `subscribeRounds` again after every reconnect.

## Reference price frames

The underlying price that crypto Up or Down rounds resolve on — Chainlink's 60-second time-weighted average price as Polymarket relays it — can be followed for assets this deployment carries. A second series, Chainlink's latest spot price, can be held beside it with the optional `bases` key (see **Reference spot basis**); this section describes the operation without that key:

```json
{"op":"subscribeReference","assets":["BTC"]}
```

```json
{"op":"unsubscribeReference","assets":["BTC"]}
```

Each frame takes from **1** through **4** `assets` (1 to 10 upper-case letters or digits). An asset this deployment does not carry refuses the whole frame with `VALIDATION_FAILED`, for `unsubscribeReference` as well as `subscribeReference`, and nothing in that frame is subscribed or unsubscribed. A listed-twice asset counts once. A connection holds at most **4** assets: a `subscribeReference` that would hold more is refused with an `error` frame whose `code` is `RATE_LIMITED` and whose `details` carry `reason` `reference_subscription_limit`, `currentSubscriptions`, and `requestedSubscriptions`. Tokens, Perps instruments, round pairs and reference assets are counted separately.

The reply to `subscribeReference` is `referenceSubscribed`:

```json
{"type":"referenceSubscribed","assets":["BTC"],"snapshot":[{"asset":"BTC","basis":"chainlink_twap_60s","points":[{"price":"118420.1","ts":1790935814000},{"price":"118420.153274","ts":1790935815000}]}],"feed":"live"}
```

For each newly held asset, `snapshot[].points` contains every point this instance holds since the start of that asset's current live round (the earliest, if rounds of several intervals are live), oldest first; with no live round for that asset, it contains every point held. Points are kept for at most the last **300** seconds by default. The snapshot may be shorter, even empty, right after a round starts or the service (re)starts: points are held in memory only, and past points are not fetched. An already-held asset is not listed again in `assets` and has no `snapshot` element; if every asset is already held the reply is `{"type":"referenceSubscribed","assets":[],"snapshot":[],"feed":"live"}` when the feed is live.

Later frames:

```json
{"type":"referencePrice","asset":"BTC","basis":"chainlink_twap_60s","price":"118420.153274","ts":1790935815000}
```

```json
{"type":"referenceFeed","state":"interrupted","ts":1790935820000}
```

```json
{"type":"referenceUnsubscribed","assets":["BTC"]}
```

`referenceUnsubscribed.assets` lists only assets the connection let go of. `basis` is a closed word that names the series a point belongs to: `chainlink_twap_60s`, or `chainlink_spot` on a connection that asked for it (see **Reference spot basis**). A connection that never sends `bases` only receives `chainlink_twap_60s`. `price` is a plain decimal string kept as the source sends it; parse it as a decimal, not a float. `ts` is the source time of the value in epoch milliseconds and only increases per asset and `basis` on one connection: an older point is not sent live. Expect about one `chainlink_twap_60s` point per second per asset. `referenceFeed` (`live` or `interrupted`, with `ts`) is sent only when the upstream state changes and only to connections holding at least one reference asset. Points missed during an interruption are not sent later (though they may appear in a later `referenceSubscribed` if still held). Show a live indicator from `feed` and `referenceFeed`, not from the arrival of frames. `referencePrice` follows the buffer rule of `price` frames and counts toward the same **4008** close; a skipped point is not sent again. These prices are for display; Polymarket settles a round, not these frames.

When reference prices are not open on this deployment, `subscribeReference` gets an `error` with `code` `NOT_FOUND` and `details.reason` `reference_not_open`; `unsubscribeReference` gets `referenceUnsubscribed` with empty `assets`. During rollout an older instance answers both operations with `VALIDATION_FAILED`; send `subscribeReference` again after every reconnect.

## Reference spot basis

`subscribeReference` takes an optional `bases` key that names the price series to hold for the listed assets:

| `basis` | What it is |
|---|---|
| `chainlink_twap_60s` | Chainlink's 60-second time-weighted average price as Polymarket relays it. This is the price a round resolves on, and the one to plot a round's `targetPrice` against. About one point per second per asset. |
| `chainlink_spot` | Chainlink's latest price as Polymarket relays it. It is for display only and is **not** the price a round resolves on. About two points per second per asset. |

```json
{"op":"subscribeReference","assets":["BTC"],"bases":["chainlink_twap_60s","chainlink_spot"]}
```

```json
{"op":"subscribeReference","assets":["BTC"],"bases":["chainlink_spot"]}
```

`bases` takes from **1** through **2** of the words above. Without the key, the frame asks for `chainlink_twap_60s` alone, exactly as it did before the key existed. A word listed twice counts once. Any other word, an empty list, or a value that is not a list refuses the whole frame with `VALIDATION_FAILED`, and nothing in that frame is subscribed. The limit of four assets per connection counts assets, not series: both series of four assets fit, and adding a series to an asset the connection already holds never reaches the limit.

The reply has one `snapshot` element per newly held series, that is, per asset and `basis`. For the two frames above, sent on two fresh connections:

```json
{"type":"referenceSubscribed","assets":["BTC"],"snapshot":[{"asset":"BTC","basis":"chainlink_twap_60s","points":[{"price":"118420.1","ts":1790935814000}]},{"asset":"BTC","basis":"chainlink_spot","points":[{"price":"118419.80","ts":1790935814210}]}],"feed":"live"}
```

```json
{"type":"referenceSubscribed","assets":["BTC"],"snapshot":[{"asset":"BTC","basis":"chainlink_spot","points":[{"price":"118419.80","ts":1790935814210},{"price":"118420.15","ts":1790935815210}]}],"feed":"live"}
```

- `snapshot` lists assets in the order the frame listed them and, within an asset, `chainlink_twap_60s` before `chainlink_spot`, whatever the order of `bases`.
- Each element follows the snapshot rule of **Reference price frames** for its own series: the same time window, oldest point first, possibly empty.
- `assets` lists the assets that got at least one new series. Sending `subscribeReference` for an asset the connection already holds, with a basis it does not hold yet, adds that series: the reply lists the asset and has a `snapshot` element for the added series only. A series already held is not listed again, and when nothing is new, `assets` and `snapshot` are both empty.
- A `subscribeReference` without `bases` on an asset held with `chainlink_spot` alone adds `chainlink_twap_60s`.
- `unsubscribeReference` lets go of an asset with every series. It has no `bases` key; one sent with it is ignored.

Later points carry their series in `basis`:

```json
{"type":"referencePrice","asset":"BTC","basis":"chainlink_spot","price":"118420.15","ts":1790935815210}
```

Read `basis` on every `snapshot` element and every `referencePrice`: both series of an asset arrive on the same connection, interleaved. `ts` only increases within one asset and `basis`, so a `chainlink_spot` point can carry a later `ts` than the `chainlink_twap_60s` point that follows it. `price` is kept as the source sends it, trailing zeros included. Spot points are sent as they arrive, without coalescing, and follow the buffer rule of every `referencePrice`: they count toward the same **4008** close, and a skipped point is not sent again.

`feed` and `referenceFeed` are one state for both series, and that state follows the `chainlink_twap_60s` series: `live` means the service's upstream is delivering the price that rounds resolve on. **`live` does not promise spot points.** An instance can serve no spot in two ways:

- During a rollout, an instance that predates `bases` ignores the key and answers as if it were absent. The `snapshot` of a newly held asset then has no `chainlink_spot` element, and every `referencePrice` carries `chainlink_twap_60s`, also when the frame asked for `chainlink_spot` alone.
- An instance whose upstream is not delivering spot answers with a `chainlink_spot` element whose `points` are empty and sends no `chainlink_spot` point. An empty element by itself is also what an instance sends right after it starts.

In both cases, fall back to `chainlink_twap_60s`. The simplest client asks for both bases, draws `chainlink_spot` while its points arrive, and draws `chainlink_twap_60s` when the reply for a newly held asset has no `chainlink_spot` element, or when no `chainlink_spot` point has arrived for a few seconds while `chainlink_twap_60s` points keep arriving. Send `subscribeReference` with `bases` again after every reconnect, because the next instance can differ.

Spot never decides a round. A round's `targetPrice`, its `polybolt_twap` estimate, and its result do not use `chainlink_spot`; plot the target against `chainlink_twap_60s`.

## Disconnections

The service closes with **4029** when a connection limit is exceeded or when the client exceeds the frame-rate limit. It closes with **1011** when it rejects a connection, including a duplicate connection ID. It closes with **1001** during server shutdown or after the heartbeat timeout. It closes with **4008** when a client's `bufferedAmount` exceeds **1048576** bytes for **100** consecutive delivery attempts. This indicates a slow consumer; catch up on reads or reduce subscriptions before reconnecting.
