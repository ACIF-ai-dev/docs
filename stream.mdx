## Connect

Upgrade `GET /v1/stream` to WebSocket and send your builder API key as a Bearer credential:

```http
Authorization: Bearer <your API key>
```

The stream requires a `trade`-scope key. Keep that key on your server: it is a credential that can reach trading and funding surfaces, not a browser or mobile-app credential.

## Connecting from a browser

Your builder backend, not the browser, sends its trade key to `POST /v1/stream/tickets`, optionally with `userId`. Pass the returned `ticket` to the browser, then connect it without an Authorization header:

```js
new WebSocket("wss://…/v1/stream?ticket=" + encodeURIComponent(ticket));
```

Tickets expire after **60 seconds** and are **one-time use**. Obtain a new ticket for every reconnect. Do not send an API-key header with a ticket. Invalid ticket upgrades return HTTP 401 before upgrade (browsers show this as close **1006**); request a fresh ticket and retry. A ticket `userId` has at most **3** simultaneous connections. A ticket issued without `userId` does not use that per-user limit and only receives the ticket per-subbuilder limit; provide `userId` when you need a per-user limit. Ticket connections have a separate per-subbuilder limit of **500** by default (key connections remain limited to **10**); either ticket limit closes with **4029**. More than **60** ticket attempts from the same IP in a minute return HTTP 429 before upgrade, and a busy ticket verifier returns HTTP 503 before upgrade; browsers show either as close **1006**. Because tickets are URL query parameters, proxy and CDN access logs can contain them; they are one-time and expire in 60 seconds, so a logged value was already used or will soon expire. Tickets are the browser-safe alternative: keep the trade key on your server.

Issuing tickets has its own rate budget: by default 600 `POST /v1/stream/tickets` requests per minute per builder account, separate from the per-key and hourly budgets your other requests use (see **Rate limits** on the API reference home page). Exceeding it returns HTTP 429 with `error.details.reason` set to `stream_ticket_limit_exceeded` and a `Retry-After` header. It is a different limit from the 60 ticket attempts per IP per minute on the upgrade above.

After the upgrade succeeds, the stream sends a `welcome` frame with a `connectionId` and `heartbeatIntervalMs`.

## Send frames

Client frames use `op` as their discriminator, not `type`:

```json
{"op":"subscribe","tokenIds":["token-id"]}
```

```json
{"op":"subscribe","tokenIds":["token-id"],"trades":true}
```

```json
{"op":"unsubscribe","tokenIds":["token-id"]}
```

```json
{"op":"ping"}
```

`trades` is optional and opts those tokens into `trade` frames (see **Trade frames** below); the only accepted value is `true`. A `subscribe` without it behaves exactly as it did before the flag existed.

`subscribe` and `unsubscribe` each require from **1** through **200** token IDs. Each token ID is a string from **1** through **128** characters. A WebSocket frame can be at most **65536** bytes (**64 KiB**).

The service accepts at most **120** client frames in each **1000 ms** window. It sends a WebSocket heartbeat every **30000 ms** and closes a connection that has not answered within **90000 ms**.

## Receive frames

Server frames use `type` as their discriminator:

```json
{"type":"welcome","connectionId":"connection-id","heartbeatIntervalMs":30000}
```

```json
{"type":"subscribed","tokenIds":["token-id"],"snapshot":[{"tokenId":"token-id","bestBid":"0.105","bestAsk":null,"ts":1727430000123}]}
```

```json
{"type":"unsubscribed","tokenIds":["token-id"]}
```

```json
{"type":"pong"}
```

```json
{"type":"price","tokenId":"token-id","bestBid":"0.105","bestAsk":null,"ts":1727430000123}
```

```json
{"type":"resolved","tokenId":"token-id","market":"market-id","winningTokenId":"token-id","winningOutcome":"Yes","ts":1727430000123}
```

```json
{"type":"trade","tokenId":"token-id","side":"BUY","price":"0.07","size":"1234.56","amountUsd":"86.4192","ts":1727430000123}
```

```json
{"type":"error","code":"VALIDATION_FAILED","message":"Invalid stream frame.","details":{}}
```

`details` on an `error` frame is optional. Ignore server frames with an unknown `type` to parse defensively.

## Market frames

A `price` frame is paired with the subscribed `tokenId`. A `best_bid_ask` event with a single `tokenId` is routed through that token. The service sends at most one `price` frame per token every **250 ms**; it keeps the newest price in that window. `resolved` frames are immediate and are not coalesced.

`bestBid` and `bestAsk` are decimal **strings**, or `null` when unavailable. Do not parse them as numbers for calculation. `ts` is epoch milliseconds: the upstream timestamp when present, otherwise the service receive time. After a snapshot, the service does not send a price with an older timestamp when both the snapshot and new price carry upstream timestamps. A price with the same value as a snapshot can follow it when that price was waiting in a coalescing window.

The `subscribed` frame includes a snapshot for each newly subscribed token with a cached price. A token without a cache entry is omitted. If the upstream sends an order book for a token that has no cached price, the service uses that book's highest bid and lowest ask as the token's first `price` frame. A token that already has a cached price ignores order books; its later prices come from best bid and ask updates. The upstream is not guaranteed to send an order book, and without one the token's first `price` frame follows the next quote change. Read an initial value from REST when a snapshot is empty.

`market_resolved` is forwarded as a `resolved` frame once for each of its subscribed token IDs. If you subscribe to both YES and NO tokens for one market, its resolution arrives in two `resolved` frames, one for each token. Process frames idempotently.

Resolved tokens are omitted from snapshots; obtain their resolution status and final price from REST.

`new_market` does not produce a frame. This is a token-level subscription service: tokens belonging to a newly created market have, by definition, not been subscribed by any client, so there is no token-level recipient to route the event to. The service does not send upstream `book`, `price_change`, or `tick_size_change` events; an upstream `book` only supplies a missing first price, as described above. An upstream `last_trade_price` becomes a `trade` frame only for connections that opted in, as described below.

## Trade frames

A `trade` frame reports one public trade on a token. It is sent only to a connection that subscribed that token with `"trades":true`; a connection that did not opt in receives no `trade` frames, and the frames it does receive are unchanged. The opt-in is per token:

| You send | Effect on `trade` frames for those tokens |
|---|---|
| `subscribe` with `"trades":true` | On, whether or not the token was already subscribed. The reply is the usual `subscribed` frame; a token that was already subscribed is not listed in it again. |
| `subscribe` without `trades` | No change. A token already opted in stays opted in. |
| `unsubscribe` | Off, together with the token's `price` and `resolved` frames. |
| `"trades"` with any value other than `true` | The whole frame is refused with `VALIDATION_FAILED`, as any invalid frame is. |

The opt-in does not count against the 200-token subscription limit separately; only the tokens do.

The frame has these keys and no others. They are the same keys, with the same meaning, as each element of `GET /v1/markets/{marketId}/trades`:

- `tokenId`: the outcome token the trade was on.
- `side`: `"BUY"` or `"SELL"`, as the source reports it.
- `price`, `size`: decimal **strings** (shares for `size`), with no exponent and no trailing zeros.
- `amountUsd`: `price` × `size` in decimal, not rounded, as a decimal string.
- `ts`: the trade time in epoch milliseconds, from the source.

`trade` frames carry no trader identity, transaction hash, or fee rate. An upstream event without a size or a trade time, or with a price or size that is not a plain decimal, is dropped rather than completed with a guessed value. Trade frames are sent as they arrive, without coalescing, and are not part of the `subscribed` snapshot. Their order relative to `price` frames is not guaranteed.

A connection receives at most **50** `trade` frames in each **1000 ms** window; trades beyond that are dropped, not queued. Trade frames are also skipped while the connection's `bufferedAmount` is over half of the **4008** close threshold below. Skipped trades never count toward that close, and they never hold back a `price` frame. A busy market can therefore show gaps in the trade feed: treat it as a live tape, not a complete record.

To show recent trades, read `GET /v1/markets/{marketId}/trades` when the view opens and subscribe with `"trades":true` before or right after that read, then add each `trade` frame to the top. The REST read and the stream can contain the same trade. With no trade ID or transaction hash in either, complete de-duplication is not guaranteed; dropping a frame whose `tokenId`, `side`, `price`, `size`, and `ts` all match an element already shown removes most repeats but can also drop a distinct trade with identical values.

While a new version of the service is being rolled out, an instance that predates the flag ignores `"trades":true` without an error: a connection that lands on it gets the usual `subscribed` frame and no `trade` frame. Keep the REST read as the source of recent trades, and send `subscribe` with `"trades":true` again after every reconnect.

## Disconnections

The service closes with **4029** when a connection limit is exceeded or when the client exceeds the frame-rate limit. It closes with **1011** when it rejects a connection, including a duplicate connection ID. It closes with **1001** during server shutdown or after the heartbeat timeout. It closes with **4008** when a client's `bufferedAmount` exceeds **1048576** bytes for **100** consecutive delivery attempts. This indicates a slow consumer; catch up on reads or reduce subscriptions before reconnecting.

## Changes

2026-10-05: `subscribe` accepts an optional `"trades":true`, and opted-in tokens receive `trade` frames built from the upstream `last_trade_price` event. Connections that do not send the flag receive exactly the frames they received before.

2026-09-29: Ticket issuance (`POST /v1/stream/tickets`) moved to its own rate budget, by default 600 requests per minute per builder account. It no longer counts against the per-key per-minute limit or the hourly `trade` budget.

2026-09-28: A token without a cached price can receive its first `price` frame from an upstream order book instead of waiting for the next quote change. Frame shapes did not change; keep reading an initial value from REST when a snapshot is empty.

2026-09-27: Browser stream tickets were added: 60-second one-time tickets, three connections per user, and a default 500 ticket connections per subbuilder.

2026-09-27: `event` frames were replaced by `price` and `resolved` frames (a breaking change). No compatibility layer was added: as of this change, no client had received `event` frames through the public route.
