## Build on prediction markets

tobuilder is B2B backend infrastructure for prediction-market builders. Its API provides wallet onboarding, deposits, orders, and withdrawals so a customer application can offer those capabilities without implementing the underlying infrastructure itself.

The API base URL is `https://api.tobuilder.app`, and it is available for requests now.

This page takes you from console sign-in to a first authenticated call using nothing but HTTP. Everything here works with `curl`; no client library is required.

## Get an API key

The public API has no key-issuance operation, and every key is created by a signed-in operator in the tobuilder console. The backend does not require or validate an invite code when provisioning an operator: a valid Privy console token is sufficient, subject to platform signup availability and rate limits.

1. **Sign in to the tobuilder console.** Sign-in identifies you as an operator of a builder account, and it is also where registration happens: an operator the console has not seen before is registered as part of signing in, so there is nothing to apply for and no approval to wait for. If the console keeps returning you to its access screen instead, that is a signal something is wrong rather than a queue you are waiting in — send the operator ID that screen shows to your tobuilder administrator.
2. **Issue an API key** in the console. A key carries a label of 1 to 64 characters after trimming, and a scope (below). Issuing and rotating keys is itself rate limited — 10 per hour by default — and each account has a maximum number of simultaneously active keys, above which issuance is refused until you revoke one or a rotation grace period ends.
3. **Store the key at once.** The plaintext key is returned exactly once, in the response to issuance. The service keeps only its hash, so a key you lose cannot be read back: revoke or rotate it and issue a new one. Keys start with the prefix `tb_live_`.

The console may present an invite-code check as an optional console UX step. Its `invite/verify` route compares the code and refuses one it does not recognise; verification is limited to 20 attempts per minute per client address. This check issues no session or token.

An API key is a server-side credential. Do not ship one to a browser, a mobile app, or any other client you do not control.

### Scopes

A key's scope decides which route prefixes it may call. Scopes are cumulative — each one includes everything below it.

| Scope | Adds | Use it for |
|---|---|---|
| `bot-read` | `/v1/markets`, `/v1/me`, `/v1/sports`, `/v1/perps/instruments`, `/v1/events` | reading market data and checking the key itself |
| `bot-link` | `/v1/users`, `/v1/onboarding`, `/v1/webhooks/endpoints` | linking your users, onboarding their wallets, and registering or rotating webhook endpoints |
| `trade` | `/v1/deposit`, `/v1/orders`, `/v1/withdrawals`, `/v1/webhooks/deliveries`, `/v1/stream`, `/v1/perps/account` | deposits, order flow, withdrawals, webhook delivery operations, the streaming surface, and Perps accounts |

Calling a route outside the key's scope returns **403**, with `error.details.reason` set to `api_key_scope_insufficient`. The check runs on the route prefix before the handler, so the same request with the same key always gets the same answer — use a key issued with the scope you need. Issue the narrowest scope that covers the job: a read-only bot does not need a key that can move money.

The streaming surface behind `/v1/stream` is documented in the [Stream guide](stream); the operations documented in this reference are the HTTP ones.

The `/v1/perps/instruments` routes are market-data reads for perpetual instruments, documented in the [Perps market data guide](perps). A deployment where that data is not open answers them with 404 and `error.details.reason` set to `perps_not_open`.

The `/v1/perps/account` routes open and read an end user's Perps account. They are a separate surface with a separate gate: they need a `trade` key and the end user's token, and while Perps accounts are not open for the caller they answer 404 with `error.details.reason` set to `perps_accounts_not_open`. See [Perps accounts](perps#perps-accounts).

The webhook routes under `/v1/webhooks` are split across two rungs: `bot-link` opens `/v1/webhooks/endpoints`, and `trade` adds the rest, including `/v1/webhooks/deliveries`.

### Rotation and revocation

Rotating a key issues a successor and keeps the previous key working for a fixed grace period of 24 hours, so you can roll the new value through your deployment before the old one stops. While a key in that lineage is still inside its grace period, the lineage cannot be rotated again — finish the roll-out first. Revoking is immediate and has no grace period: the revoked key fails on its next request.

Like issuance, rotation returns the new plaintext key exactly once. If it is lost, revoke the new key and issue another.

## Get an end-user token

User-facing operations under `/v1/users/*`, `/v1/deposit/*`, `/v1/withdrawals/*`, and `/v1/perps/account` need the builder key plus an `x-end-user-token` header. The header value is that end user's Privy access token.

Your frontend obtains the token by signing the user in through the single Privy app that tobuilder provides for this integration; your tobuilder administrator gives you the app id. Before login, send every frontend origin — including a development origin such as `http://localhost:<port>` — to your tobuilder administrator so it can be registered in Privy's allowed origins. Login fails for an unregistered origin; that is registration state, not a bug. Send the origin again when the domain changes.

If a token is rejected, see the 401 description in the **API reference** for the listed reason codes.

## Authenticate

Send the key as a Bearer credential on every request:

```http
Authorization: Bearer <your API key>
```

Operations that act on behalf of one of your end users need a second credential, the `x-end-user-token` header, carrying that user's Privy access token. Both headers are required on those operations: a missing or blank `x-end-user-token` is **401** with `error.details.reason` set to `end_user_token_missing`, and a missing or unrecognised builder key is **401** as well. The **API reference** lists the credentials each operation requires.

## Rate limits

Three budgets apply, and all of them are fixed windows rather than sliding ones. Stream ticket issuance (`POST /v1/stream/tickets`) is counted only against the third. Five reads, `GET /v1/markets`, `GET /v1/markets/{marketId}`, `GET /v1/markets/rounds`, `GET /v1/events/{eventId}` and `GET /v1/perps/account`, are counted only against the first. Every other request is counted against the first and, when the key is a `trade` key, the second; the two apply independently.

**Per key, per minute.** Every request except stream ticket issuance is counted against the key's own per-minute limit. `GET /v1/me` reports that limit as `rateLimitPerMinute`. Responses that reach the limiter carry `RateLimit-Limit`, `RateLimit-Remaining`, and `RateLimit-Reset`.

**Per account, per hour, for `trade` keys.** A `trade`-scope key is additionally limited to 600 requests per hour by default, counted per builder account in a window that resets at the top of the hour. Five reads are outside this budget: `GET /v1/markets`, `GET /v1/markets/{marketId}`, `GET /v1/markets/rounds`, `GET /v1/events/{eventId}` and `GET /v1/perps/account` are not counted against it and are not rejected when it is exhausted, so an account whose orders this budget is refusing can still read its market list; the per-minute limit still applies to all five. Nothing else under `/v1/markets`, `/v1/events` or `/v1/perps` is outside it — a market's order book and fee preview, both price histories, the Perps market-data reads and `POST /v1/perps/account` count. Every other request except stream ticket issuance counts against the budget — including the other GET requests, and including the requests that are themselves rejected with 429 by this budget. A tight retry loop therefore spends the budget it is waiting for. Exceeding it returns **429** with `error.details.reason` set to `trade_hourly_limit_exceeded`.

**Stream tickets, per account, per minute.** `POST /v1/stream/tickets` has its own budget of 600 ticket requests per minute by default, shared by every key of the builder account, in a window that resets at the start of each minute. Issuing tickets therefore does not spend the per-minute or hourly budget your orders use. Every ticket request that reaches this budget counts — including requests rejected with 429 and requests the operation then rejects, such as an unknown `userId`. Its responses carry `RateLimit-Limit`, `RateLimit-Remaining`, and `RateLimit-Reset` for this budget. Exceeding it returns **429** with `error.details.reason` set to `stream_ticket_limit_exceeded`.

`Retry-After` is a number of seconds, and it is not on every 429. A limit-exceeded response (per-minute, hourly, or stream ticket) carries it. A 429 raised because the limiter itself is unavailable does not, and neither does `order_idempotency_in_flight`, which means another submission holding the same lock is in flight rather than "you are over a limit". Read the header when it is there; do not assume a value when it is not.

## Your first call

`GET /v1/me` confirms the key works and reports its per-minute limit.

```bash
curl https://api.tobuilder.app/v1/me \
  -H "Authorization: Bearer $TOBUILDER_API_KEY"
```

```json
{
  "subbuilderId": "sb_example",
  "apiKeyId": "key_example",
  "name": "production-bot",
  "rateLimitPerMinute": 120
}
```

The key is read from the environment on purpose. A key typed into a command line survives in shell history, and a key put in a URL survives in access logs; it belongs in the `Authorization` header and nowhere else.

## Browse markets

```bash
curl "https://api.tobuilder.app/v1/markets?limit=5&category=politics" \
  -H "Authorization: Bearer $TOBUILDER_API_KEY"
```

```json
{
  "markets": [
    {
      "marketId": "0x9a1c-example",
      "question": "Will this example market resolve YES?",
      "category": "politics",
      "active": true,
      "endDate": "2026-12-31T00:00:00.000Z",
      "outcomes": [
        { "outcome": "Yes", "price": "0.42", "tokenId": "71453-example", "oneHourPriceChange": "-0.0125" },
        { "outcome": "No", "price": "0.58", "tokenId": "71454-example", "oneHourPriceChange": null }
      ],
      "syncedAt": "2026-09-13T00:00:00.000Z",
      "icon": "https://polymarket-upload.s3.us-east-2.amazonaws.com/example-icon.png",
      "image": null,
      "volume24h": "2672.1804860000007",
      "eventStartTime": "2026-10-02T10:10:00.000Z"
    }
  ],
  "total": 1,
  "syncedAt": "2026-09-13T00:00:00.000Z"
}
```

The example is abridged; the API reference lists every field of a market. Each outcome carries `outcome`, `price`, `tokenId` — the CTF token id you pass as `tokenId` to the order operations — and `oneHourPriceChange` (see below). Choose the outcome by its `outcome` label, never by array position; a `null` `tokenId` means that outcome cannot be traded. Note that `/v1/markets` declares `limit` and `offset` as strings, while `/v1/users/positions` declares `limit` as an integer and pages with a `cursor`; the reference is authoritative per operation.

### Order, sorting, and filters

The list has a fixed order: most recently synced first and, among markets synced together, by `marketId`. One catalog sync stamps the markets it stores with the same time, so `marketId` decides most of that order; it is compared as text and the order it gives carries no meaning. Because the order is total, paging with `limit` and `offset` returns every market exactly once while the catalog does not change between your requests. A sync between two page requests can still move markets, and a page may be served from the route cache, so a walk taken across a sync can repeat or miss a market.

Three optional query parameters reorder or narrow the list. They combine with each other and with `category`, and `total` counts the markets that match them.

| Parameter | Value | Effect |
| --- | --- | --- |
| `sort` | `volume24h` | Largest `volume24h` first, compared as numbers. Markets whose `volume24h` is `null` come last, and markets with the same volume are ordered by `marketId`. Without `sort` the list keeps the default order above. |
| `tag` | one tag slug | Only markets that carry that slug in `tags[].slug`. Exact and case-sensitive: a slug does not match a longer slug that starts with it or the same letters in another case, and labels are not searched. At most 100 characters, made of letters, digits, hyphen, underscore, and dot. |
| `game` | `true` or `false` | `true` returns only game markets, `false` only the others; without it both are returned. A game market is one whose `sportsMarketType` is not `null`. |

Any other value is a 400 `VALIDATION_FAILED`: a `sort` that is not `volume24h`, a `tag` that is empty, too long, or holds another character, a `game` that is not `true` or `false`. A tag no listed market carries is not an error; the list is empty and `total` is `0`. Take slugs from `tags[].slug` in the responses rather than guessing them.

```bash
# Trending: highest 24-hour volume first.
curl "https://api.tobuilder.app/v1/markets?sort=volume24h&limit=20" \
  -H "Authorization: Bearer $TOBUILDER_API_KEY"

# A crypto home: one tag, by volume.
curl "https://api.tobuilder.app/v1/markets?tag=crypto&sort=volume24h" \
  -H "Authorization: Bearer $TOBUILDER_API_KEY"

# A sports season view: markets tagged sports that are not single games.
curl "https://api.tobuilder.app/v1/markets?tag=sports&game=false" \
  -H "Authorization: Bearer $TOBUILDER_API_KEY"
```

Sorting by volume orders the values the catalog sync last read (see below), not live figures.

### Market images

Each market, in the list and from `GET /v1/markets/{marketId}`, carries `icon` and `image`: the market's images from Gamma, each an absolute `https` URL or `null`. The two may be the same URL. `null` means Gamma sent no image, sent one this service did not accept, or the market was last stored before these fields existed; show your own placeholder.

- **Use the URL only as an image source** (`<img src>`), exactly as received. Do not fetch it and insert its contents into your page, and do not build image URLs from the host or path yourself.
- **The host can change.** The URL points at an image store, not at this API, and the service may later move images to its own origin; code that expects a particular host will break. In a sample of Gamma data taken on 2026-09-26, every image URL that was not empty was on `https://polymarket-upload.s3.us-east-2.amazonaws.com`, and it is the only host this service passes through today.
- **Content Security Policy.** If your page or mini app sets an `img-src` directive, add that host to it (for example `img-src 'self' https://polymarket-upload.s3.us-east-2.amazonaws.com`). If the host changes, images are blocked until the directive is updated, so treat a failed image like a `null` one.
- A URL that is not `null` can still fail to load. Handle the image's error event with the same placeholder.

### One-hour price change

Each element of `outcomes`, in the list and from `GET /v1/markets/{marketId}`, carries `oneHourPriceChange`: Gamma's change in price over the last hour, as Gamma computes it.

- **Only the first outcome has a value.** Gamma reports one change per market, and in the samples this service has kept it follows the price of the first element of `outcomes`. The second element's `oneHourPriceChange` is always `null`; the service does not derive it from the first. If you show a change for the second outcome, that is your own calculation.
- **A signed decimal from -1 to 1.** The value is a signed decimal string from `"-1"` to `"1"` with no exponent, such as `"-0.1745"` or `"0.005"`. In the samples this service has kept it reads as the new price minus the old one, on the same 0 to 1 scale as `price`: a first outcome now at `0.0255` carried `"-0.1745"`, which fits a move down from `0.2`. The service has not measured Gamma's definition beyond those samples and does not recompute the value. Parse it as a decimal rather than a floating-point number; Gamma's figure can carry floating-point noise in its last digits, and the service passes the digits through as they came.
- **`null` on the first element means unknown, not zero.** Gamma sent no value for the market, sent one that is not a number from -1 to 1 or whose decimal form is longer than 64 characters, or the market was last stored before this field existed or by an older version of the service. Do not show `null` as no change.
- **It is as fresh as the catalog sync.** The value is read when the sync stores the market, not when you call; the market's own `syncedAt` is the time of that reading.
- **Several choices.** An event with several choices is several markets, one per choice, each named by `groupItemTitle` and sharing `event.id`. The change of a choice is the first element's `oneHourPriceChange` of that choice's market.
- **Game markets.** Totals and spreads markets are not in this list; `GET /v1/markets/{marketId}` serves them from a separate sync of Gamma's event data, which refreshes on its own schedule. In the samples of that data this service has kept, Gamma sent the value on some of them and left it out of others.

### 24-hour volume

Each market, in the list and from `GET /v1/markets/{marketId}`, carries `volume24h`: the market's trading volume over the last 24 hours, as Gamma reports it.

- **A decimal string or `null`.** The string is a non-negative decimal with no exponent and no sign, such as `"0"` or `"2672.1804860000007"`. Gamma sends this figure as a number, and it often carries more decimal places than a currency has; round it for display, and parse it as a decimal rather than a floating-point number if you calculate with it.
- **`null` means unknown, not zero.** Gamma sent no value for the market, sent one that is not a non-negative number or whose decimal form is longer than 64 characters, or the market was last stored before this field existed. Do not show `null` as `0`.
- **It is as fresh as the catalog sync.** The value is read when the sync stores the market, not when you call; the market's own `syncedAt` is the time of that reading.
- **Game markets.** Moneyline game markets are in this list and get the value from the same sync as every other listed market. Totals and spreads markets are not in this list; `GET /v1/markets/{marketId}` serves them from a separate sync of Gamma's event data, which refreshes on its own schedule, and in the samples of that data this service has kept Gamma left the value out of most of them, so expect `null` there often.
- **Unit.** The value is passed through without conversion. The Gamma data this service reads does not state a unit; the service treats Gamma's volume figures as US dollars.

### Event start time

Each market, in the list and from `GET /v1/markets/{marketId}`, carries `eventStartTime`: the Gamma market field of the same name, as an ISO 8601 UTC timestamp such as `2026-10-02T10:10:00.000Z`, or `null`.

- **It is no other field.** The service copies Gamma's `eventStartTime` into it and nothing else. It is separate from `gameStartTime` and `endDate` and is never filled from them, so the two start times of one market are not guaranteed to be equal. The service passes on the instant Gamma reports under that name and adds no meaning of its own; compare it with the markets you show before you build a countdown on it.
- **`null` means unknown.** Gamma sent no value for the market, sent one that is not a timestamp with a time zone, or the market was last stored before this field existed. Handle `null` as an ordinary case, not as an error, and do not show another field in its place without deciding that yourself.
- **It is as fresh as the catalog sync.** The value is read when the sync stores the market, not when you call; the market's own `syncedAt` is the time of that reading.
- **Game markets.** Totals and spreads markets are not in this list; `GET /v1/markets/{marketId}` serves them from a separate sync of Gamma's event data. In the samples of that data this service has kept, Gamma sent the field on none of them, so expect `null` there.

## Read a market's rules and its event

`GET /v1/markets/{marketId}` carries `rules`: the market's rules text and the link to its settlement source, as Gamma publishes them. `GET /v1/markets` does not carry it.

```bash
curl "https://api.tobuilder.app/v1/markets/0x9a1c-example" \
  -H "Authorization: Bearer $TOBUILDER_API_KEY"
```

```json
{
  "marketId": "0x9a1c-example",
  "question": "Will this example market resolve YES?",
  "rules": {
    "description": "This market will resolve to \"Yes\" if the upper bound of the target rate is cut.\n\nThe resolution source is the statement the Federal Reserve publishes after its meeting.",
    "resolutionSource": "https://www.federalreserve.gov"
  }
}
```

The example is abridged to the market's `rules`.

- **`description` is plain text.** Show it as text; do not render it as HTML or markdown. `\n` breaks a line, and one or more of them separate paragraphs. It is Gamma's whole text, in English, not a summary. `null` means Gamma sent none or an empty one, the text is longer than 10,000 characters (it is not cut), or the market was last stored before this field existed.
- **`resolutionSource` is a link.** When it is not `null`, it is an absolute `https` URL of the source the market settles against; use it only as a link. Many markets have none, so expect `null` often and show nothing in its place.
- **`rules.translation`.** With `lang`, `rules` also carries `translation`: a translation of `description` into that language, or `null` when none of the current text is stored. When it is `null`, show `description`. It does not depend on the question's `translation`.

`GET /v1/events/{eventId}` returns one event and the markets of it that the catalog lists, each with the keys of `GET /v1/markets/{marketId}`, `rules` included. `eventId` is the `event.id` of a market; use this read for an event screen that shows all of its choices.

```bash
curl "https://api.tobuilder.app/v1/events/903193" \
  -H "Authorization: Bearer $TOBUILDER_API_KEY"
```

```json
{
  "event": {
    "id": "903193",
    "slug": "fed-decision-in-december",
    "title": "Fed decision in December?",
    "endDate": "2026-12-10T00:00:00.000Z"
  },
  "markets": [
    { "marketId": "0x9a1c-example", "groupItemTitle": "25 bps decrease", "rules": { "description": "…", "resolutionSource": null } }
  ],
  "truncated": false
}
```

- **Listed markets only.** A market of the event that `GET /v1/markets` leaves out is not here either, although `GET /v1/markets/{marketId}` can still return it by its `marketId`.
- **Order and size.** The markets are ordered by `marketId`, at most 200. `truncated` is `true` when the event has more listed markets than that; those past the first 200 are not returned.
- **The event object.** `slug` and `title` are those stored with the event's markets, and `endDate` is the latest `endDate` among the markets returned: when the event ends, as far as the service knows. Each is `null` when no market has one.
- **`lang`** applies to each market as on `GET /v1/markets/{marketId}`.
- **Not found.** An event with no listed market is a 404 `NOT_FOUND`.
- **Rate limits.** This read is outside a `trade` key's hourly budget, like the single-market read; the per-minute limit still applies. The event's price history is counted against both (see **Rate limits**).

```json
      ]
    },
    {
      "outcome": "No",
      "tokenId": "71454-example",
      "status": "ok",
      "bestBid": "0.956",
      "bestAsk": "0.957",
      "midpoint": "0.9565",
      "spread": "0.001",
      "minOrderSize": "5",
      "tickSize": "0.001",
      "negRisk": false,
      "bids": [
        { "price": "0.956", "size": "2100" },

```

Bids and asks are returned best first: bids are sorted descending by price, while asks are sorted ascending by price.

`depth` is the requested upper bound for levels per side, so the response can contain fewer levels.

`status` is `ok` for a readable book, `no_book` when the outcome has no CLOB order book, and `no_token` when the outcome has no token ID.

The `/v1/markets` response returns `outcomes[].price` as a snapshot; this route returns the order book.

This route reads an order book once. To keep one on screen, hold the outcome's `tokenId` on `/v1/stream` with `subscribeBook` rather than polling this route; see **Order book frames** in the [Stream guide](stream).

## Read recent trades

```bash
curl "https://api.tobuilder.app/v1/markets/0x9a1c-example/trades?limit=3" \
  -H "Authorization: Bearer $TOBUILDER_API_KEY"
```

```json
{
  "marketId": "0x9a1c-example",
  "fetchedAt": "2026-10-05T12:00:00.000Z",
  "trades": [
    { "tokenId": "71453-example", "side": "BUY", "price": "0.55", "size": "10", "amountUsd": "5.5", "ts": 1791201598000 },
    { "tokenId": "71454-example", "side": "SELL", "price": "0.44", "size": "250", "amountUsd": "110", "ts": 1791201591000 },
    { "tokenId": "71453-example", "side": "BUY", "price": "0.07", "size": "1234.56", "amountUsd": "86.4192", "ts": 1791201591000 }
  ]
}
```

Trades are returned newest first. `limit` is an integer from 1 to 50 and defaults to 10; the response can contain fewer trades.

Each trade carries six keys and nothing about who traded: `tokenId` names the outcome, so read its label from the same market's `outcomes[]`. `amountUsd` is `price` × `size`, computed in decimal and not rounded; parse `price`, `size`, and `amountUsd` as decimals. `ts` is in milliseconds, but the source reports whole seconds, so several trades can share a `ts`.

This is a recent sample read from the Polymarket Data API, not a complete or live feed. One read per market is served for about two seconds (`fetchedAt` is that read), and the delay between a trade and the source listing it has not been measured.

A `502` whose `error.details.reason` is `trades_market_ids_missing` means the catalog does not yet hold the identifiers the source is asked with; it is not an answer that the market has no trades. An empty `trades` array is that answer.

`GET /v1/markets/{marketId}/price-history` returns past prices of a market's outcomes, and `GET /v1/events/{eventId}/price-history` returns the price of the first outcome (Yes on a Yes or No market) of each market in an event, for one closed `range`: `1h`, `6h`, `1d`, `1w`, or `max` (all the history the source keeps). The resolution of each range is fixed by the service; start and end times cannot be chosen, and query keys other than `range` and `lang` are ignored. `ts` is epoch milliseconds; `price` is a probability string from 0 to 1 — parse it as a decimal; converting it to a number is acceptable only to place a point on a chart. Points are in ascending `ts` order, with at most one point per `ts` and at most 1000 points per series. `eventId` is the `event.id` of a market in `GET /v1/markets`.

**Joining the live tail.** History is served from a cache and from Polymarket's own CDN, so its last point can be a few minutes old; `fetchedAt` says when each series was read. Continue the line with the `price` frames of `/v1/stream`: a display point is the midpoint of `bestBid` and `bestAsk`, and a frame where either is null adds no point. History points and stream frames come from different sources, so the line can step where they meet.

**Empty is not an error.** An empty `points` array means there was no price in that range — a new market, or a token Polymarket has no history for. `status: no_token` means the outcome has no token. In an event response, `status: unavailable` means that one market could not be read this time; its line is left empty rather than filled with an older value.

**Which markets an event response covers.** The series are the markets of the event that this service's catalog lists, at most 8, ordered by the current price of that first outcome; `omitted` counts the listed markets cut by that cap. Because prices move, the order can change from one request to the next — key colours and legend entries by `marketId`, not by position. Markets of the event that the catalog does not list — the catalog keeps markets above a trading-volume threshold — are not included and not counted.

**When it is not available.** A 404 with `error.details.reason` `price_history_not_open` means price history is not open on this deployment; retrying does not change it. That 404 is counted against the key's per-minute limit and, for a `trade` key, its hourly budget like any other request, so stop calling the route after the first one and hide the chart until your deployment changes. A 404 without `error.details` on this path can also mean the deployment you reached does not have the route yet — do not cache it. A 429 with `price_history_limit_exceeded` or `price_history_capacity` is this service's own budget for reading Polymarket; a read answered from the cache does not spend it. Wait for `Retry-After`. Do not retry a 502 immediately; when its reason is `clob_rate_limited`, its `Retry-After` says when reads resume.


`GET /v1/markets/rounds` lists the recurring short-window crypto Up or Down markets this deployment carries. Each element of `data` is one `asset` and `interval` pair, in the order the deployment lists them, with the `current` round, up to **2** `next` rounds, soonest first, and up to **5** `past` rounds, newest first. A round is one market with two outcome tokens; `eventStartTime` and `endDate` are the start and end of its window. The values in the example are made up; only the shape is real.

**Query.** Both parameters are optional; without them every pair is returned. `asset` is one asset in upper case, such as `BTC`: 1 to 10 letters or digits. `interval` is the length of the rounds, and `5m` is the only value. While rounds are open, a value of another form, a repeated parameter, or an `asset` and `interval` that select no pair this deployment carries is a 400 `VALIDATION_FAILED`.

**Rounds and their status.** `status` is `upcoming` before `eventStartTime`, `live` from `eventStartTime` up to `endDate`, then `ended` until Polymarket settles the round and `resolved` once it has. The first three are computed from the two times by the service's clock when it answers; `resolved` goes with a non-null `winningOutcome`, which is one of the round's `outcomes[].outcome` labels and is `null` until then. `next` and `past` hold only rounds the service has already read, so they can be shorter than their limits, for example right after the service starts. A round's `slug` names that one round and does not change.

**Target price.** `targetPrice` is the price the round resolves against, as Polymarket publishes it, in US dollars as a decimal string; this endpoint never computes, estimates, or rounds it. Parse it as a decimal, not as a floating-point number. It is `null` before the round starts and is usually still `null` while the round is live: Polymarket fills it in around or after the end of the round. It also stays `null` when it was not published within 20 minutes of the end. `targetPriceSource` says where the value came from and is `null` exactly when `targetPrice` is. This endpoint returns only `polymarket` or `null`. When the deployment enables it, the stream's round frames (`subscribeRounds`) can instead carry `polybolt_twap`, an estimate pinned from the stream's reference price at the round's start, from a round's start until Polymarket publishes its value; Polymarket's value then replaces it as `polymarket`, never the other way, so this list and the stream can differ for a while. See **Crypto round frames** and **Reference price frames** in the stream guide. A non-null `targetPrice` with `targetPriceSource` `polymarket`, and a non-null `winningOutcome`, are final: keep them, and do not overwrite them with a `null` from a later response.

**Freshness.** The service reads the rounds from Polymarket on its own schedule, never because of a request, and `fetchedAt` says when it last read a round of the pair. A new target price or result reaches the list after Polymarket publishes it and the service reads it again, so it can arrive minutes after the round ends. Each instance of the service keeps its own copy of the rounds: two requests that reach different instances can disagree for a short while, which is why a final value must not be replaced by a later `null`.

**Prices, trades, and settlement.** The list carries no prices. Subscribe to a round's `outcomes[].tokenId` on `/v1/stream` with `subscribe` for its `price` frames (best bid and ask), add `"trades":true` for its `trade` frames, and read its settlement from `resolved` frames. The stream also offers `subscribeRounds`, which sends the same pairs as this list and a `roundUpdate` frame whenever a round appears, changes status, gets its target price (possibly an estimate; see **Target price**), or gets its result; see the stream guide. Subscribe to the tokens of `next[0]` before it starts, so there is no gap when it becomes `current`. A running volume for a live round is the sum of `amountUsd` over the `trade` frames you received for its tokens; the stream can drop trades on a busy connection, so treat that sum as an indication, not a settled figure.

**The market routes.** These markets are not in `GET /v1/markets`. `GET /v1/markets/{marketId}` and its `/book`, `/trades`, `/price-history`, and `/fee-preview` answer for a round's `marketId` while the round is in the instance's memory — the current round, the next 2, or the past 5 of a pair — and answer 404 once it has left that window. They also answer 404 for a round whose event title, active flag, or outcome prices the service could not read, even while it is listed. A round's market has `question` and `event.title` set to the round's event title, its window in `eventStartTime` and `endDate`, and `null` or empty for what a round does not carry, such as `category`, `tags`, `volume24h`, `icon`, and `image`. Its `outcomes[].price` is a snapshot from the service's last read of the round and can be minutes old while the round is live; read live prices from the stream. Because each instance keeps its own copy, a round one instance answers can be a 404 on another: do not cache a 404 that follows a 200. With `lang=ko`, the outcome labels stay `Up` and `Down`. Orders on a round's tokens are placed like any other market's.

**When it is not available.** A 404 with `error.details.reason` `rounds_not_open` means crypto rounds are not open on this deployment, and that answer comes before the query is checked; retrying does not change it, so hide the rounds view and do not cache the answer as a fact about a pair. A 404 without `error.details` can mean the instance you reached predates this route and read `rounds` as a market identifier; do not cache it. `state: "unavailable"` means the service has not yet read that pair's current round from Polymarket, and `current` is then `null`; a 502 whose `error.details.reason` is `gamma_unavailable` means no requested pair could be read. Neither carries `Retry-After`, and retrying does not cause a read; try again after a few seconds. The list is outside the hourly budget of `trade` keys (see **Rate limits**) but counts against the key's per-minute limit, and every key scope can read it.

## Onboard one of your users

Orders are placed for an end user, so that user needs a wallet first. Onboarding is asynchronous: this call enqueues the work and returns a job.

1. Sign the end user in with Privy and obtain an access token.
2. Call `POST /v1/users/link` with the builder key and `x-end-user-token`, using `{}` as the body. The only declared body field is the optional `telegramUserId`:

   ```bash
   curl -X POST https://api.tobuilder.app/v1/users/link \
     -H "Authorization: Bearer $TOBUILDER_API_KEY" \
     -H "x-end-user-token: $END_USER_TOKEN" \
     -H "Content-Type: application/json" \
     -d '{}'
   ```

   ```json
   { "userId": "9f1d2c3b-4a5e-4f60-9b7c-8d0e1f2a3b4c", "created": true }
   ```

   The returned `userId` is the identifier you must save in your user record.
3. Call `POST /v1/onboarding {"userId":"9f1d2c3b-4a5e-4f60-9b7c-8d0e1f2a3b4c"}`.
4. Poll `GET /v1/onboarding?userId=9f1d2c3b-4a5e-4f60-9b7c-8d0e1f2a3b4c`.
5. Use that same `userId` for every later order and query.

The `userId` is an identifier issued by tobuilder at `POST /v1/users/link`, not your internal id. If you send a value that link did not return, `POST /v1/onboarding` is immediately rejected with **400** and `error.code` `VALIDATION_FAILED` (`User was not found.`); it is not silently accepted. A new onboarding job returns **201**, while an existing job for that user returns **200**. The worker-side `onboarding_external_user_id_missing` failure can occur only if the user's record disappears after the job has been queued.

```bash
curl -X POST https://api.tobuilder.app/v1/onboarding \
  -H "Authorization: Bearer $TOBUILDER_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"userId":"9f1d2c3b-4a5e-4f60-9b7c-8d0e1f2a3b4c"}'
```

## Place an order

Order submission requires an `idempotency-key` header. **You generate each key**; the service never makes one for you, and neither does the SDK. Create it before you send, store it with the intent to order, and reuse that stored value if your process restarts mid-flight — that is what makes a reconnect a replay instead of a second order.

The constraints are enforced on the trimmed value: it must be 1 to 200 characters after trimming and must not contain a comma. An absent or blank value is rejected as `order_idempotency_key_missing`; a value that is too long or contains a comma is rejected as `order_idempotency_key_invalid`. Because the trimmed value is what gets stored and compared, two keys differing only in surrounding whitespace are the same key.

A limit order:

```bash
curl -X POST https://api.tobuilder.app/v1/orders \
  -H "Authorization: Bearer $TOBUILDER_API_KEY" \
  -H "Content-Type: application/json" \
  -H "idempotency-key: 3f1b0c7a-9f3d-4f3a-9d1e-2a7c6b4e51d8" \
  -d '{"userId":"9f1d2c3b-4a5e-4f60-9b7c-8d0e1f2a3b4c","marketId":"0x9a1c-example","tokenId":"71453-example","side":"BUY","price":"0.42","size":"10"}'
```

```json
{
  "orderId": "0x4d2f-example",
  "userId": "9f1d2c3b-4a5e-4f60-9b7c-8d0e1f2a3b4c",
  "marketId": "0x9a1c-example",
  "tokenId": "71453-example",
  "side": "BUY",
  "price": "0.42",
  "size": "10",
  "createdAt": "2026-09-13T00:00:01.000Z"
}
```

A market order is a different route with a different body — a BUY needs `amount` and `maxPrice`, a SELL needs `shares` and `minPrice` — and it needs **a different idempotency key**:

```bash
curl -X POST https://api.tobuilder.app/v1/orders/market \
  -H "Authorization: Bearer $TOBUILDER_API_KEY" \
  -H "Content-Type: application/json" \
  -H "idempotency-key: b2e4d6c8-1a5f-4c9b-8e07-5d3f2a1c9b40" \
  -d '{"userId":"9f1d2c3b-4a5e-4f60-9b7c-8d0e1f2a3b4c","marketId":"0x9a1c-example","tokenId":"71453-example","side":"BUY","orderType":"FOK","amount":"25.00","maxPrice":"0.55"}'
```

```json
{
  "orderId": "0x77b1-example",
  "userId": "9f1d2c3b-4a5e-4f60-9b7c-8d0e1f2a3b4c",
  "marketId": "0x9a1c-example",
  "tokenId": "71453-example",
  "side": "BUY",
  "amount": "25.00",
  "maxPrice": "0.55",
  "createdAt": "2026-09-13T00:00:02.000Z"
}
```

`POST /v1/orders` and `POST /v1/orders/market` **share one idempotency namespace**, keyed on your account and the key alone — the route is not part of the key. Sending a key on one route that you already used on the other replays that stored order when the compared fields match, and fails with `order_idempotency_key_conflict` when they do not. In neither case does the order you just wrote reach the market. Never reuse a key across the two routes; the two examples above deliberately use different values.

Prices, sizes, amounts, and `tokenId` are strings in both directions, and they stay strings. A token id can be dozens of decimal digits; converting it to a `number` loses precision, just as it does for real-money values.

## When a call fails

Every error response uses one envelope:

```json
{
  "error": {
    "code": "VALIDATION_FAILED",
    "message": "Order size failed validation.",
    "requestId": "req_example",
    "details": { "reason": "order_size_invalid" }
  }
}
```

Branch on `error.code`, which is one of `VALIDATION_FAILED`, `UNAUTHORIZED`, `FORBIDDEN`, `NOT_FOUND`, `CONFLICT`, `RATE_LIMITED`, `INTERNAL`, and `UPSTREAM_UNAVAILABLE`. `error.details.reason` narrows the cause within a code, and each operation's reference page lists the reasons that operation can produce. Treat `details` as optional: schema validation failures and uncaught internal failures omit it. Log `error.requestId` — it is what identifies the request when you ask for support.

### When the account is suspended

A suspended account answers **403** with `error.details.reason` set to `subbuilder_suspended`, and the suspension is not scoped to one surface: orders, withdrawals, and streams stop along with console access. What it stops is new requests — work that was already accepted before the suspension, such as a withdrawal that is already in flight, is not cancelled by the suspension. Retrying does not lift it, and your tobuilder administrator can tell you why it is suspended.

### Retrying is your decision

**Nothing in this API retries for you**, and the SDK does not retry either. Three reasons:

1. **Rate budget.** The hourly budget counts GET requests — all but the five reads named under **Rate limits** — and counts rejected requests, so an automatic retry spends the budget on the failure instead of on your next real call.
2. **Money.** `POST /v1/orders` and `POST /v1/orders/market` submit real funds. After a 5xx you do not know whether the submission was stored, so a blind retry can duplicate an order; read `GET /v1/orders` and `GET /v1/orders/fills` back before sending anything again.
3. **429 is not uniform.** Some 429 responses carry `Retry-After` and some do not, so any single backoff policy baked into a client would be wrong for half of them.

## Collateral is pUSD

`GET /v1/users/collateral-balance` returns `collateralBalanceBaseUnits`: an integer string in the collateral token's base units, exactly as the venue reports it. The collateral token is **pUSD**. Keep it a string and divide with a decimal library when you display it.

`GET /v1/users/portfolio-value` is a different quantity — a mark-to-market valuation, not a balance. Its field is named `portfolioValueUsdc`; that spelling is the published contract and is reproduced here verbatim, but what it carries is a valuation figure. A `null` there means the upstream returned no value for that wallet. It is **not zero**, and rendering it as 0 misstates the account.

## Profit and loss

Two reads give an end user's PnL — realized plus unrealized PnL on their prediction-market wallet; deposits and withdrawals are not PnL. Amounts are decimal strings in US dollars; keep them strings and use a decimal library, as with collateral.

- `GET /v1/users/pnl/today?dayStart=<epoch seconds>` — the change since the start of the user's day. **"Today" is the day on the user's device**: send `dayStart` as the epoch seconds of midnight in the device's own time zone (it must lie between 26 hours before and 5 minutes after the time of the request). The answer echoes the `dayStart` it used.
- `GET /v1/users/pnl/series?range=1D|1W|1M|1Y|ALL` — cumulative PnL points for a chart, oldest first, with the change over the range. `1D` starts at `dayStart`, which it requires; the other ranges do not use it.

When the wallet has no PnL point at or before `dayStart` — its history starts later that day, or it has none yet — the start of the day counts as **0**. When the total is unavailable but the realized part is known, the realized part is still returned next to a `null` total. A `null` amount is **not zero**: `unavailableReason` says why, and a `null` point in a series is a gap in the chart. Polymarket publishes PnL points on an hourly grid, so the newest value can be up to about an hour behind the request; `asOf` says when it was taken. `parts` lists the sources the total adds up — only `prediction` today; a `perps` part will be added later, and the total stays the sum of the listed parts.
